# gb-4102 重采样对照 · 测试报告

日期：2026-11-20　环境：真实 MySQL 8.0.42（aarch64）+ Redis 7.0.15，本地起 backend/worker，非 Docker。

## 验证方式
1. 服务层回归：`python3 test-artifacts/gb-4102/test_comparison.py`（需 DATABASE_URL / REDIS_URL / JWT_SECRET）。连跑两次，均为 15/15 通过，且结束后无残留 `telemetry_cmp_*` 副本表。
2. 接口 + worker 端到端：登录 operator → 创建 `index` 与 `comparison` 各一条 → worker 真实执行 → 读取证据与导出。
3. 空库冷启动：删除并重建 `indextrial` 后启动 API，确认迁移跳过缺失表、种子 3 用户 / 3 负载 / 3 候选 / 5,000 遥测、`/health` 返回 200。
4. 前端：对真实接口载荷做无头渲染检查，比较页与队列页无 `undefined` / `NaN`，模块导入图完整、全部 `node --check` 通过。

## 关键结果（默认偏斜 1,500 行、聚焦传感器 17）
| 阶段 | 访问方式 | 估计扫描行 | 实查读取行 | 返回行 |
|---|---|---|---|---|
| 重新采样前（`FLUSH TABLE` 重载旧统计） | 全索引扫描 `PRIMARY` | 5061 | 6501 | 1550 |
| 重新采样后（`ANALYZE`） | 索引范围扫描 `trial_cmp_candidate` | 1550 | 1550 | 1550 |

两侧结果 SHA-256 一致；`verification` 全部为真：自动采样已隔离、重采样被观察到、重采样前已查到新增遥测、两侧索引结构一致。

三个种子负载在偏斜 1,500 行时均能出对账一致的结论：泵站17 与阀组59 出现计划改变，电机36 计划未变（同样是可下结论的有效结果）。

## 中断与重测
- 在 `pre_measured` 后模拟崩溃：留存副本可核验，续跑标志为真且完成对账。
- 崩溃后若 `ANALYZE` 已实际执行（重采样生效但成绩未保存）：续跑被拒绝（「重新采样前统计状态已改变」），worker 记录作废尝试并整对重测；检查点序列为 `pre_measured → retest_pair → pre_measured → resampled → completed`。
- 续跑权限：只有 operator/admin；已完成试验返回 409，索引试跑返回 400。

## 已知边界
- 对照依赖 `FLUSH_TABLES` 权限来还原「上一次采样」的统计；缺失时试验明确失败而非给出错误结论。已有数据卷需重建或手工授权。
- InnoDB 在插入后会立即更新内存行数估计，因此若不做 `FLUSH TABLE`，就无法构造「统计仍停留在旧采样」的真实状态——这一点在实现中已用真实库验证。
- 是否发生计划翻转取决于偏斜量与成本的临界点，并非每次都能复现事故；对照页只陈述两次实测事实，不承诺必然翻转。
